## 1. Executive Summary

This document represents the completion of **PASS 1 (Inspection and Impact Analysis)** for migrating the **School Examination Marks and Report Card Management System** database layer from MySQL 8.x (InnoDB) to PostgreSQL (15/16+).

### Key Findings:
1. **100% Logical Model Preservation:** The approved **23-table relational architecture** can be completely and faithfully represented in PostgreSQL without adding, removing, or combining any tables.
2. **Zero Blockers Identified:** No requirement, design conflict, or relational limitation exists that would block a faithful migration to PostgreSQL.
3. **High Semantic Parity with Specific Adjustments:**
   - **Data Types:** MySQL `BIGINT UNSIGNED AUTO_INCREMENT` maps directly to PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
   - **JSON:** MySQL `JSON` maps directly to PostgreSQL `JSONB` with superior indexing and integrity.
   - **Functional Uniqueness:** MySQL 8.0 functional key parts using `COALESCE` for nullable `section_id` in `class_subjects` and nullable `term_id`/`assessment_id` in `generated_reports` map natively to PostgreSQL expression-based unique indexes (`CREATE UNIQUE INDEX ... (..., COALESCE(col, 0), ...)`).
   - **Referential Integrity:** All 43 foreign keys with `ON DELETE RESTRICT ON UPDATE RESTRICT` translate directly to PostgreSQL ANSI-standard restrictive constraints.
   - **CHECK Constraints:** All 7 verified domain CHECK constraints use standard ANSI SQL expressions that translate identically to PostgreSQL.
4. **Specific PostgreSQL Migration Nuances Identified:**
   - **Collation / Case-Sensitivity (HIGH Risk):** MySQL's `utf8mb4_unicode_ci` collations prevent case-variant duplicate usernames, subject names, and role names (e.g. `admin` vs `ADMIN`). PostgreSQL's default collation is case-sensitive. Case-insensitive unique indexes (e.g., `LOWER(username)`) or `citext` are required to maintain the exact business semantics.
   - **Automatic Timestamp Updates (`updated_at`) (HIGH Risk):** MySQL provides native `ON UPDATE CURRENT_TIMESTAMP`. PostgreSQL lacks this column-level clause. A single reusable trigger function (`moddatetime` or a standardized trigger procedure) or explicit application handling is required.
   - **Test Harness Redesign (MEDIUM Risk):** The MySQL validation suite relies on MySQL-specific error numbers (`1062`, `3819`, `1451`, `1265`) and stored procedure error handlers. In PostgreSQL, this must be re-architected using PostgreSQL standard `SQLSTATE` codes (`23505`, `23514`, `23503`, `22P02`) inside PL/pgSQL anonymous `DO $$` blocks.
5. **Separation of Baseline:** The `database/MySQL/` directory remains strictly untouched as the permanent historical baseline. PASS 1 creates only documentation under `database/Postgres/`.

## 6. BRD / Business Rule Constraints Relevant to Migration

The following critical business rules dictate specific database behaviors that must not be altered during migration:

1. **Mark State Triage (BR-009 to BR-014):**
   - Exactly three states: `blank` (incomplete, mark value must be NULL), `numeric` (completed, mark value must be non-negative), and `absent` (completed, mark value must be NULL, calculates as 0).
   - No additional states (`EX`, `WH`, `NA`) may be introduced.
2. **Dynamic Terms (BR-032 to BR-035):**
   - The school may have any number of terms (e.g., 2 semesters, 3 terms, 4 quarters). Terms are ordered strictly by `sequence_no ASC`. No hard-coding to 3 terms.
3. **Assessment Applicability & Maximum Marks (BR-018 to BR-021):**
   - Maximum marks belong to `assessment_applicability`, not `assessments`, because maximum marks vary by subject within the same test.
4. **Term Percentage Calculation Participation (BR-023 to BR-028):**
   - Display selection on report cards is separate from calculation participation.
   - **Only the Term Exam contributes to the term percentage**.
5. **Historical Placements & Transfers (BR-037 to BR-041):**
   - Internal transfers (8A → 8B) preserve the 8A record with status `internal_transfer` and roll 15; create a new 8B record with status `active` and roll 22. Historical marks stay linked to the 8A placement.
6. **Subject Name Snapshot (BR-047):**
   - `class_subjects.subject_name_snapshot` protects historical report cards from future master subject renames.
7. **Report PDF Revision Integrity (BR-059, BR-060):**
   - PDFs are never overwritten. A modified report generates Revision 2, leaving Revision 1 intact on disk and in `generated_reports`.
8. **Multi-Scope Teacher Authorizations (BR-001, BR-002, BR-003):**
   - A teacher can hold multiple assignment rows. Class Teacher assignments grant class-wide access to all applicable subjects automatically (`subject_id IS NULL`).
9. **Restrictive Referential Actions:**
   - No cascading deletes. Deactivating users or closing academic years must never purge historical records.

## 9. Primary Key / Identity Strategy

In MySQL, all 23 tables define primary keys using `BIGINT UNSIGNED NOT NULL AUTO_INCREMENT`.

### PostgreSQL Identity Options Evaluated:

1. **`BIGINT GENERATED ALWAYS AS IDENTITY`:**
   - *Behavior:* PostgreSQL strictly enforces that the database generates the value. Any `INSERT` statement providing an explicit `id` value will error out unless `OVERRIDING SYSTEM VALUE` is specified.
   - *Drawback:* Makes baseline seed data loading, historical test migrations, and backup restorations cumbersome.

2. **`BIGINT GENERATED BY DEFAULT AS IDENTITY` (RECOMMENDED):**
   - *Behavior:* If an `INSERT` statement specifies an `id`, PostgreSQL accepts it; if the `id` is omitted or `DEFAULT` is passed, PostgreSQL automatically generates the next value from the sequence.
   - *Advantage:* Standard ANSI SQL compliance; perfectly accommodates seed data (e.g. `roles` with fixed IDs 1 to 4) while seamlessly auto-generating IDs for normal application inserts.
   - *Sequence Synchronization:* After loading explicit seed rows, `SELECT setval(pg_get_serial_sequence('roles', 'id'), coalesce(max(id), 1)) FROM roles;` cleanly resynchronizes the sequence.

### Decision:
All 23 tables in PostgreSQL will use:
```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

There are 8 distinct `ENUM` columns in the reference MySQL schema:

| Table | Column | Allowed Values | Business Meaning |
|---|---|---|---|
| `academic_years` | `status` | `'open'`, `'closed'` | Academic year lifecycle. Closed makes teachers read-only. |
| `subjects` | `category` | `'main'`, `'elective'` | Subject categorization for student allocation. |
| `student_academic_records` | `status` | `'active'`, `'internal_transfer'`, `'withdrawn'`, `'transferred_out'` | Historical student placement tracking. |
| `student_subject_allocations` | `allocation_type` | `'main'`, `'elective'` | Student's applicable subject offering. |
| `assessments` | `status` | `'active'`, `'inactive'` | Assessment lifecycle status. |
| `teacher_assignments` | `assignment_type` | `'subject_teacher'`, `'class_teacher'` | Teacher authorization scope. |
| `marks` | `result_status` | `'blank'`, `'numeric'`, `'absent'` | Critical 3-state mark tracking. |
| `calculation_settings` | `calculation_method` | `'average_percentage'`, `'combined_marks'` | Approved class term calculation formula. |
| `report_configurations` | `report_type` | `'exam'`, `'term'`, `'final'` | Scope of report card layout. |
| `generated_reports` | `report_type` | `'exam'`, `'term'`, `'final'` | Type of historical generated PDF. |

### Architectural Options for PostgreSQL:

1. **Approach A: Custom PostgreSQL Types (`CREATE TYPE ... AS ENUM`):**
   - *Pros:* Strict database-level type safety, compact 4-byte internal storage, clean DDL.
   - *Cons:* Adding values requires `ALTER TYPE ... ADD VALUE` (which cannot be executed inside a multi-statement transaction in older PG versions); dropping values requires recreation; types live in schema namespace.
2. **Approach B: `VARCHAR(N)` with Table-Level `CHECK` Constraints:**
   - *Pros:* Fully transactional, easily modified via `ALTER TABLE ... DROP/ADD CONSTRAINT`, highly portable, zero custom type clutter.
   - *Cons:* Slightly larger storage (negligible for small lookup strings), repetitive check definitions if used across multiple tables (e.g., `report_type`).

### Recommendation:
- Use **`CREATE TYPE ... AS ENUM`** for core stable domain types that are finalized by the BRD:
  - `academic_year_status` (`'open'`, `'closed'`)
  - `subject_category` (`'main'`, `'elective'`)
  - `student_placement_status` (`'active'`, `'internal_transfer'`, `'withdrawn'`, `'transferred_out'`)
  - `assessment_status` (`'active'`, `'inactive'`)
  - `teacher_assignment_type` (`'subject_teacher'`, `'class_teacher'`)
  - `mark_result_status` (`'blank'`, `'numeric'`, `'absent'`)
  - `calculation_method_type` (`'average_percentage'`, `'combined_marks'`)
  - `report_type_enum` (`'exam'`, `'term'`, `'final'`)
- This provides identical type safety and rejects invalid entries with `SQLSTATE '22P02'` (invalid text representation).

## 12. DATETIME / TIMESTAMP Analysis

The schema utilizes timestamps across multiple tables:
- `created_at` (audit log, record creation)
- `updated_at` (record modification)
- `last_login_at` (user login history)
- `generated_at` (PDF generation timestamp)

### PostgreSQL Analysis:
1. **`TIMESTAMPTZ` (TIMESTAMP WITH TIME ZONE) (RECOMMENDED):**
   - Stores the absolute UTC epoch microsecond timestamp internally.
   - Automatically converts to the configured session timezone on display.
   - Essential for historical audit logs and PDF generation timestamps, ensuring immunity to Daylight Saving Time shifts or multi-region client access.
2. **The `ON UPDATE CURRENT_TIMESTAMP` Nuance (HIGH RISK):**
   - In MySQL: `updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`.
   - In PostgreSQL: There is **no native column-level attribute** for auto-updating on row modification.
   - *PASS 2 Strategy Options:*
     - **Option 1 (DB-Level Trigger):** Create a generic trigger function:
       ```sql
       CREATE OR REPLACE FUNCTION trigger_set_updated_at()
       RETURNS TRIGGER AS $$
       BEGIN
           NEW.updated_at = CURRENT_TIMESTAMP;
           RETURN NEW;
       END;
       $$ LANGUAGE plpgsql;
       ```
       Attach this trigger `BEFORE UPDATE` to tables with `updated_at`.
     - **Option 2 (Application-Level):** Application/ORM sets `updated_at = NOW()` on every update.
     - *Recommendation:* To maintain strict behavioral parity with the MySQL baseline where direct SQL updates auto-update `updated_at`, implement the single generic trigger function in PostgreSQL.

## 13. Character Set / Collation Analysis

### The Case-Insensitivity Hazard (HIGH RISK):
- In MySQL: The database is configured with `COLLATE utf8mb4_unicode_ci` (`_ci` = Case Insensitive).
  - A query `SELECT * FROM users WHERE username = 'admin'` matches `'ADMIN'`, `'Admin'`, and `'admin'`.
  - An insert of `'Admin'` when `'admin'` exists is rejected by `UNIQUE KEY uk_users_username`.
- In PostgreSQL: The default collation (`default` or `en_US.UTF-8`) is **case-sensitive**!
  - Under standard PostgreSQL `UNIQUE (username)`, the database will allow `'admin'`, `'Admin'`, and `'ADMIN'` as three separate users.
  - This violates the intended security and uniqueness model for usernames and role names!

### Solutions Evaluated for PostgreSQL:
1. **Case-Insensitive Expression Indexes (RECOMMENDED FOR CRITICAL IDENTIFIERS):**
   ```sql
   CREATE UNIQUE INDEX uq_users_username_lower ON users (LOWER(username));
   CREATE UNIQUE INDEX uq_roles_name_lower ON roles (LOWER(name));
   CREATE UNIQUE INDEX uq_subjects_name_lower ON subjects (LOWER(name));
   ```
   - Ensures case-insensitive uniqueness without requiring special cluster-level collations.
2. **`citext` Extension:**
   - Provides a case-insensitive `VARCHAR` type (`CITEXT`).
   - Requires `CREATE EXTENSION IF NOT EXISTS citext;`.
   - Adds an extension dependency.
3. **ICU Non-Deterministic Collations:**
   - PostgreSQL 12+ supports `CREATE COLLATION case_insensitive (provider = icu, locale = 'und-u-ks-level2', deterministic = false);`.
   - Cannot be used on columns with pattern-matching operations (`LIKE` with non-deterministic collations has restrictions).

### PASS 2 Recommendation:
Use standard PostgreSQL `CREATE UNIQUE INDEX ... (LOWER(column))` for unique identity fields (`users.username`, `roles.name`, `subjects.name`) to guarantee strict case-insensitive uniqueness.

## 14. NULL Semantics Analysis

In standard SQL (and PostgreSQL), `NULL` values in a unique constraint are considered distinct. Two rows with `NULL` in the same unique column do not violate a `UNIQUE` constraint.

### Affected Tables in Current Model:
1. `class_subjects.section_id`:
   - Class-wide offerings have `section_id IS NULL`.
   - Two class-wide offerings for the same academic year, class, and subject would both have `section_id = NULL`.
   - A standard unique index on `(academic_year_id, class_id, section_id, subject_id)` would **NOT** prevent duplicates in PostgreSQL!
2. `generated_reports.term_id` and `assessment_id`:
   - Final reports have `term_id IS NULL` and `assessment_id IS NULL`.
   - A standard unique index would not prevent duplicate Revision 1 records for final reports.

### Resolution:
See Sections 18, 19, and 20. PostgreSQL's expression indexes using `COALESCE` completely resolve this issue identically to MySQL 8.0.

- Total foreign keys in MySQL: **43**.
- Policy across all 43 foreign keys: **`ON DELETE RESTRICT ON UPDATE RESTRICT`**.
- **PostgreSQL Compatibility:**
  - PostgreSQL natively supports `ON DELETE RESTRICT ON UPDATE RESTRICT`.

    ```sql
    CONSTRAINT fk_sar_student
        FOREIGN KEY (student_id) REFERENCES students (id)
    ```

  - Zero risk. 100% semantic identity.

## 18. Functional Unique Constraint Mapping

MySQL 8.0 allows functional key parts directly inside `CREATE TABLE ... UNIQUE KEY (col1, (COALESCE(col2, 0)))`.
In PostgreSQL:
- An expression cannot be declared inside an inline table `CONSTRAINT ... UNIQUE (...)`.
- Instead, PostgreSQL uses an **expression-based unique index**:
  ```sql
  CREATE UNIQUE INDEX index_name ON table_name (col1, (COALESCE(col2, 0)));
  ```
- This index enforces strict relational uniqueness at the storage engine level identically to a unique constraint.

## 19. `class_subjects.section_id` NULL Uniqueness Analysis

- **The Problem:** In `class_subjects`, `section_id` is NULL for class-wide offerings and non-NULL for section-specific offerings. Multiple rows with `section_id = NULL` would be permitted under a regular unique constraint in PostgreSQL.
- **MySQL 8.0 Reference Baseline:**
  ```sql
  UNIQUE KEY `uk_class_subjects_config` (`academic_year_id`, `class_id`, (COALESCE(`section_id`, 0)), `subject_id`)
  ```
- **PostgreSQL Equivalent:**
  ```sql
  CREATE UNIQUE INDEX uq_class_subjects_config 
  ON class_subjects (academic_year_id, class_id, COALESCE(section_id, 0), subject_id);
  ```
- **Verification:**
  - For section-specific rows, `section_id` is $> 0$.
  - For class-wide rows, `COALESCE(section_id, 0)` is `0`. Only one class-wide row can exist per `(academic_year_id, class_id, subject_id)`.
  - Identical behavior. Zero semantic gap.

## 20. `generated_reports` Revision Identity Analysis

- **The Problem:** `generated_reports` tracks revisions across three report types:
  - Term reports: `term_id` is populated; `assessment_id` is NULL.
  - Exam reports: `assessment_id` is populated; `term_id` may be NULL.
  - Final reports: both `term_id` and `assessment_id` may be NULL.

  ```sql
      student_academic_record_id,
      report_type,
      COALESCE(term_id, 0),
      COALESCE(assessment_id, 0),
      revision_number
  );
  ```
- **Verification:** Guaranteed unique revision identity across all three report types.
